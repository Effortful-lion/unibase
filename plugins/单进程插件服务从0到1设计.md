# 单进程内部插件系统：从 0 到 1 的设计

## 1. 文档定位

本文设计一个运行在单个服务进程内的“内部能力插件系统”。插件由同一组织开发和维护，用来提供文件处理、媒体转换、数据分析、通知等可复用能力。

插件不是动态加载的第三方代码，而是宿主程序中的独立模块。业务系统只依赖插件契约，不依赖插件内部实现。本文暂不引入服务发现、节点调度、消息队列和插件市场。

## 2. 目标与非目标

### 2.1 目标

- 用统一方式注册、查找和调用插件。
- 插件拥有明确的输入、输出、错误和版本契约。
- 插件通过宿主注入的能力访问存储、数据库和事件系统。
- 同步任务可以直接返回，长任务可以在进程内异步执行。
- 每个插件独立限流、超时、取消和日志记录。
- 失败任务可重试，重复请求不会产生不可控的重复副作用。

### 2.2 非目标

- 不支持不可信第三方代码直接加载到进程。
- 不实现多节点负载均衡和服务发现。
- 不实现通用 DAG 工作流编排器。
- 不把所有业务逻辑都改造成插件。

## 3. 核心概念

| 概念 | 含义 |
|---|---|
| 插件 | 实现一个清晰业务能力的执行单元，例如 `image.resize` |
| 宿主 | 注册插件、校验请求、执行插件、统一处理结果的服务 |
| 插件契约 | 输入、输出、错误、版本和所需能力的定义 |
| 能力接口 | 宿主授予插件的受控依赖，例如对象存储或事件发布器 |
| 同步调用 | 请求等待插件完成并直接得到结果 |
| 异步任务 | 请求只创建任务，稍后查询状态或接收通知 |
| 衍生物 | 插件根据输入对象生成的新对象，例如缩略图 |

插件应按“业务能力”划分，而不是按底层工具划分。`image.resize` 是插件；ImageMagick 或 FFmpeg 是插件内部的实现适配器。

## 4. 单进程总体架构

```text
业务系统
   |
   | HTTP / RPC / 进程内调用
   v
插件宿主
   ├── 插件注册表
   ├── 请求路由与参数校验
   ├── 权限、幂等、超时、取消
   ├── 每插件并发限制
   ├── 同步执行器
   ├── 异步任务管理器
   ├── 能力容器
   └── 统一日志、指标和错误处理
        |
        ├── 具体插件：image.resize、video.transcode ...
        ├── 对象存储适配器
        ├── 数据库适配器
        ├── 事件/Webhook 适配器
        └── 外部命令适配器
```

第一版可以只提供 HTTP API；如果宿主和业务逻辑在同一进程，也可以保留一个类型安全的进程内调用入口。无论哪种入口，都必须经过同一个宿主执行流程。

## 5. 插件契约

每个插件至少声明名称、版本、输入输出类型、执行模式和所需能力：

```json
{
  "name": "image.resize",
  "version": "1.0.0",
  "execution": "sync_or_async",
  "timeoutSeconds": 120,
  "permissions": ["object.read", "object.write"]
}
```

推荐使用强类型输入和输出：

```go
type ResizeInput struct {
    SourceObject string `json:"sourceObject"`
    Width        int    `json:"width"`
    Height       int    `json:"height"`
    Fit          string `json:"fit"`
}

type DerivativeOutput struct {
    ObjectID    string            `json:"objectId"`
    ContentType string            `json:"contentType"`
    Size        int64             `json:"size"`
    Metadata    map[string]string `json:"metadata,omitempty"`
}
```

新增可选字段可以增加小版本；删除字段、改变字段含义或改变错误语义必须升级主版本。

## 6. 插件接口

插件接口只描述执行，不暴露 HTTP、数据库连接池或消息客户端：

```go
type Plugin interface {
    Manifest() Manifest
    Execute(ctx context.Context, input json.RawMessage, caps Capabilities) (Result, error)
}
```

宿主负责：

1. 根据名称和版本查找插件。
2. 解析和校验输入。
3. 检查调用方权限与插件能力白名单。
4. 生成 `requestID`、`taskID` 和幂等键上下文。
5. 执行超时、取消、并发限制和资源限制。
6. 统一记录状态、耗时、错误和结果引用。

插件负责：

- 校验业务参数之间的关系。
- 使用宿主注入的能力完成工作。
- 返回结构化结果和可分类错误。
- 对相同幂等键保持可重复执行的结果。

## 7. 注册与调用

### 7.1 注册

插件在进程启动时显式注册：

```go
host.Register(NewResizePlugin())
host.Register(NewWatermarkPlugin())
```

注册时应检查：名称格式、版本格式、名称是否重复、能力是否在宿主允许范围内。重复注册必须启动失败，不能静默覆盖。

### 7.2 同步调用

```http
POST /v1/plugins/image.resize:invoke
Idempotency-Key: file-123:resize:640x480
Authorization: Bearer ...

{
  "sourceObject": "obj://bucket/file-123",
  "width": 640,
  "height": 480,
  "fit": "contain"
}
```

成功响应：

```json
{
  "requestId": "req_abc",
  "status": "succeeded",
  "result": {"objectId": "obj_456", "contentType": "image/jpeg"}
}
```

### 7.3 异步调用

长任务返回 `202 Accepted`：

```json
{
  "requestId": "req_abc",
  "taskId": "task_789",
  "status": "queued"
}
```

客户端通过 `GET /v1/tasks/{taskId}` 查询。通知不是第一版必需能力；需要通知时，由宿主在状态变更后调用 Webhook 或发布事件。

## 8. 宿主如何与其他系统交互

### 8.1 对象存储

插件只使用对象 ID，不拼接存储系统内部 URL：

```go
type ObjectStore interface {
    Open(ctx context.Context, id string) (ObjectReader, error)
    Put(ctx context.Context, meta ObjectMeta, body io.Reader) (string, error)
    Head(ctx context.Context, id string) (ObjectMeta, error)
}
```

原始对象只读，处理结果写成新对象。结果记录保存源对象、插件版本、参数摘要和输出对象。

### 8.2 数据库

插件不直接持有全局数据库连接。需要业务数据时，通过按领域划分的接口访问，例如 `UserReader`、`OrderWriter`。宿主可以为不同插件注入不同的接口集合，避免插件获得过大的权限。

### 8.3 事件和 Webhook

事件表达已经发生的事实，如 `image.derivative.created`。事件内容只放 ID、状态和结果引用，不放大文件。消费者必须允许重复消费，并使用事件 ID 或业务幂等键去重。

### 8.4 外部命令

FFmpeg、ImageMagick 等工具通过适配器调用。参数使用参数数组传递，禁止将用户输入拼接为 shell 命令；每次调用设置超时、临时目录、输出大小和退出码映射。

## 9. 单进程异步任务

第一版不需要消息队列，可以使用进程内任务管理器：

```text
queued -> running -> succeeded
              |-> retrying -> queued
              |-> cancelled
              |-> failed
```

任务状态可以先存数据库；如果暂时没有数据库，至少应有可替换的 `TaskStore` 接口，不能把任务状态散落在插件自身的内存变量中。

最小任务字段：

| 字段 | 作用 |
|---|---|
| `task_id` | 唯一任务 ID |
| `plugin_name/version` | 执行契约 |
| `input` | 脱敏后的输入快照 |
| `idempotency_key` | 防止重复创建任务 |
| `status` | 当前状态 |
| `attempt` | 执行次数 |
| `result` | 结果引用 |
| `error` | 分类错误摘要 |
| `created_at/updated_at` | 生命周期审计 |

进程重启时，`running` 任务应被扫描并恢复为 `retrying` 或 `failed`。只对临时错误重试；参数、权限和格式错误直接失败。带外部副作用的插件必须通过幂等键避免重复操作。

## 10. 能力注入

能力接口是插件和宿主之间最重要的隔离边界：

```go
type Capabilities struct {
    Objects ObjectStore
    Events  EventPublisher
    Clock   Clock
    Logger  Logger
}
```

宿主按插件清单过滤能力。例如只给缩略图插件 `object.read` 和 `object.write`，不给它用户管理或支付能力。测试时可以注入 fake 实现，因此插件业务逻辑不依赖真实基础设施。

## 11. 并发、超时与资源管理

- 每个插件有独立的最大并发数，避免单个重任务占满进程。
- 同步调用必须设置请求超时；异步任务设置任务级超时。
- 所有外部资源使用 `defer` 或等价机制释放。
- 临时文件按任务隔离，并在成功、失败、取消后清理。
- 外部进程必须等待退出并收集有限大小的标准错误输出。
- 大文件插件应限制同时读写的文件数和磁盘空间。

## 12. 安全与可观测性

内部插件也不能默认拥有全部权限：

- 调用方和插件能力分别鉴权。
- 原始对象只读，禁止默认覆盖。
- 禁止 shell 拼接和任意路径写入。
- 日志不记录令牌、完整文件内容和敏感输入。
- 每次调用携带 `requestID`，异步任务额外携带 `taskID`。
- 记录插件名、版本、状态变化、耗时、错误类别和结果引用。

核心指标包括调用量、成功率、延迟、当前并发、任务积压、重试率、结果大小和外部工具失败率。

## 13. 测试策略

- 契约测试：输入校验、输出结构和错误码。
- 宿主测试：注册、路由、权限、限流、超时和取消。
- 插件单测：业务参数和结果判定，外部工具使用 fake adapter。
- 任务测试：重试、取消、幂等和进程重启恢复。
- 集成测试：使用测试对象存储和测试数据库验证完整链路。
- 压测：单进程并发、长任务积压和临时文件清理。

## 14. 推荐的第一版目录

```text
plugin-service/
├── cmd/server/              # 服务入口
├── host/                    # 注册、路由、执行、权限、限流
├── plugin/                  # Plugin、Manifest、Result、错误模型
├── task/                    # 状态机、任务存储、进程内 worker
├── capability/              # 存储、事件、时钟、日志接口
├── transport/http/          # 对外 HTTP API
├── plugins/                 # 具体内部插件
└── adapters/                # 数据库、对象存储、外部工具适配器
```

## 15. 从 0 到 1 的实施顺序

1. 定义一个插件的输入、输出、错误和能力清单。
2. 实现进程内注册表和统一 `Invoke` 流程。
3. 增加参数校验、超时、取消、并发限制和结构化日志。
4. 接入对象存储适配器，完成一个真实插件闭环。
5. 增加 `TaskStore` 和进程内 worker，支持异步任务。
6. 增加幂等、重试、任务查询和结果记录。
7. 补齐契约测试、插件单测和故障测试。

## 16. 未来演进边界

只有当单进程遇到明确瓶颈时，才拆出队列和独立执行节点。届时可以保留现有 `Plugin`、`TaskStore` 和 `Capabilities` 契约，在宿主外增加调度层、节点心跳和租约。

这意味着分布式化是部署方式的变化，不应迫使业务系统重新理解插件能力。第一版的成功标准是：插件契约稳定、宿主可控、任务可恢复、结果可引用。
